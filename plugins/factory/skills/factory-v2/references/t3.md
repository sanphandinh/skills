# T3 Code

Verified on T3 Code 0.1.9 (Beta, macOS) with Claude as the coordinator and Claude, Cursor and Antigravity workers. Read smode's `harness/t3.md` first: it covers spawning, routes, work orders for other providers and quota, and this reference builds on it. Use the `t3-code` tools of the coordinator's thread; they load late, so look each one up once before you call it absent.

## Before the first wake

- **The coordinator is one thread for life.** Tasks belong to the thread that started them (`task_status` and `task_cancel` refuse another thread's tasks), so never move the factory to a new thread while workers live. Record this thread's id (`parentThreadId` in `orchestrator_capabilities`) as `t3-coordinator` in the memory index.
- **It runs in the project root**, not in a worktree: every worker's worktree starts from the commit this checkout is at. The coordinator never edits code, so the checkout stays clean.
- **Runtime mode `full-access`** (or `auto`) on this thread: workers inherit it, and an approval request is never routed to the coordinator, so a supervised worker stalls on its first command.
- **Worktree cleanup** on in T3's settings (Settings → Worktrees → Cleanup: after the thread settles, after merging), as a second net behind close-workspace.
- **Worktree branch naming**: a static prefix (Settings → Worktrees), so T3 does not rename a worker's branch while it works.

## Operations

| Operation | T3 Code |
|---|---|
| open-workspace | In the main checkout: `git fetch origin`, then `git merge --ff-only origin/<trunk>` (stop and say so when it is not a fast-forward). The workspace itself is created by start-worker: every step is a fresh worktree. The ticket's branch on the remote carries the work between steps, and every work order names it: "start with `git fetch origin`; when `origin/<branch>` exists, `git reset --hard origin/<branch>`; push with `git push origin HEAD:<branch>`". |
| start-worker | `delegate_task` with the work order as `task`, `title` `<number> <role>`, `role` (`design` for planner, `implementation` for implementer, `test` for verifier, `review` for reviewer), `isolation: "worktree"`, `target` the candidate **Routing** picked (`providerInstanceId`, `model`, `options`), `clientRequestId` `<number>-<role>-<round>`, `mode: "async"`. Record the `taskId` and `childThreadId` in the memory index under `live workers`. |
| wait-events | Nothing to call. A finished worker starts a new turn in this thread ("Delegated task … [completed]" or "[failed]"); a question arrives as a notice; a watched pull request wakes it too. Each such turn is a wake. |
| send | `t3_thread_send` to the worker's `childThreadId`, `mode: "auto"`, only to a running worker. On a provider that steers (Claude, Cursor), it reaches the running turn; on one that cannot (Antigravity and other ACP agents) it is queued (`delivery: "queued"`) and the worker reads it only when its current turn ends, as a new turn. A finished worker is never sent new work: start a fresh one. |
| inspect | One worker: `task_status` (`status`, `workState`, `summary`, `hasPendingQuestion`), and `t3_thread_read` on its `childThreadId` with `view: "activity"` and a small `limit` for its last output and its `error` items. Every worker: `task_status` for each `taskId` under `live workers`. Providers able to take work: `orchestrator_capabilities` (a provider with `constraints` cannot). |
| flag-human | `t3_thread_organize` `pin` on this thread and `t3_thread_update` `rename` with a `⏸ <number>` prefix, plus the brief on the tracker. `mark_unread` fails while this thread's turn is running, which is always the case during a wake; the turn's end notifies the phone instead. Clear: `unpin`, rename back. |
| stop-worker | `task_cancel` with its `taskId`. |
| close-workspace | Find the worktree: `git worktree list --porcelain`, the path whose branch is the worker's (`t3/…`). Run the push check there, then `git worktree remove <path>`, `git branch -D <its branch>`, and `t3_thread_organize` `archive` on its `childThreadId`. |
| resume | The coordinator thread does not change. A new session in it (a fresh-session wake, a restart) reads `live workers` from the memory index and inspects each; a live worker keeps its step. |
| schedule-wakes | The watcher (below). Cancel it with `schedule_task` (`scheduledTaskId`, `enabled: false`) to pause, `delete_scheduled_task` to stop. |

## Events

- A turn that starts with "Delegated task <taskId> (<title>) [completed]": `done`. Its result is the file its work order names; the `summary` is its report.
- "[failed]": `failed`. Before **Failed workers**, read its `error` items for a usage limit (**Quota** in the playbook; smode's `harness/t3.md` lists the words).
- "… is blocked on a question": `question`. `t3_pending_request` `read` with the `threadId` and `requestId` it names, then `respond` with `answers` keyed by the question's `id`.
- A watched pull request's wake: the board changed; go on with the wake.
- No event at all for a worker whose `task_status` is `running` past `Wake timeout` with no new activity: `blocked`.

## Wakes: the watcher

T3's scheduler has no pre-wake check: every run is a model turn. So the schedule runs a cheap **watcher** thread, and only the watcher decides whether the coordinator wakes.

1. Write `<memory>/wake-check.sh`. It fingerprints what a wake would act on (open issues and pull requests with `gh … --json number,updatedAt,labels,headRefOid`, trunk's head through `gh api repos/<owner>/<repo>/commits/<trunk> --jq .sha`, `ls -lA <memory>/results`: `-lA`, never `-la`, whose `..` line is the memory folder, whose time changes each time the fingerprint is written, so every run would wake), keeps the fingerprint in `<memory>/wake-fingerprint`, and exits 0 when it changed or the file is at least an hour old, 1 otherwise. Workers' outcomes need no fingerprint: they wake the coordinator themselves.
2. `schedule_task` with `title` `factory watch: <repo>`, `schedule` `{type: "interval", everyMs: <Wake timeout in ms>}`, `bindToCurrentThread: false`, `freshSession: true`, and this prompt (fill the paths and the id):

   > Factory watcher. Run `sh <memory>/wake-check.sh`. When it exits 1, reply `quiet` and stop. When it exits 0, list the queue of thread `<coordinator thread id>` with `t3_queue` `list`; when a message containing `factory-v2` waits there, reply `already queued` and stop. Otherwise send that thread, with `t3_thread_send` `mode: "queue"`, the message `<wake prompt>`, and reply `woke`.

3. Run it once (`run_scheduled_task_now`), find the watcher thread it made (`t3_thread_list`, `titleContains: "factory watch"`), and move that thread to the `scout` route's first candidate with `t3_thread_configure` (`modelSelection`). Later runs follow that thread's model. Record the task id and the watcher thread id as `t3-wake` and `t3-watcher` in the memory index.

**Wake prompt.** With Claude as the coordinator and the `factory` plugin installed for it: `$factory:factory-v2 once`. Otherwise, or when unsure: `Read <absolute path of factory-v2/SKILL.md> and run it in mode once.` Both start a wake; the second works on every provider.

## Resume test (setup smoke test)

1. Start worker `smoke sleeper` (`sleep 600`, then report), and record its `taskId` under `live workers`.
2. `schedule_task` with `schedule` `{type: "once", runAt: <now + 2 minutes>}`, `bindToCurrentThread: true`, `freshSession: true`, and the prompt "Factory resume test: read the memory index, call `task_status` on every task under `live workers`, write the results to `<memory>/results/resume.json`, and reply with the file's path."
3. PASS when the file shows the sleeper as `running`: a fresh session in the coordinator's thread sees its live workers.

## Traps

- `isolation: "worktree"` starts from this checkout's commit, not from `origin`: a stale trunk here is a stale base for every worker.
- A finished child keeps its thread, but a new round is always a new `delegate_task`; T3's own guidance says so, and a follow-up to a finished child does not reopen its task.
- Approvals are not routed; questions are. A Cursor worker has no question tool at all (smode's `harness/t3.md`).
- `interactionMode: "plan"` is not a read-only guard: never set it.
- Antigravity's file tools refuse paths outside the worktree, its shell starts outside it (T3's attachments folder), and it has written outside it; work orders say to run every command from the checkout, and the provider check records `pwd`.
- Every coordinator turn that ends sends a "finished" notification to the phone; snooze the coordinator thread to keep them quiet.
- T3 has no tool that deletes a worktree; close-workspace does it with git.
