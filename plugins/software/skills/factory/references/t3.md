# T3 Code

Verified on T3 Code 0.1.12 (server, macOS) with Claude coordinators and dispatchers, and Claude, Cursor and Antigravity workers. T3 runs a provider's own agent and adds one orchestration layer through its `t3-code` tools; the factory is the only skill that uses it to run sessions. Use the `t3-code` tools of your own thread; they load late, so look each one up once before you call it absent.

`res` is `node <factory>/scripts/resources.mjs --root <main checkout>`, as in DISPATCHER.md.

## Before the first wake

Setup checks each of these and fixes what it can; what only a person can set, it asks for and checks again.

- **The project.** `t3_project_list` finds the T3 project whose `workspaceRoot` is the main checkout. Record its id as `t3-project` in the memory index.
- **Setup scripts wait.** `t3_project_read`: every script with `runOnWorktreeCreate: true` must have `async: false`. Only then does T3 hold a new thread's first turn until the script finished; a script without it runs beside the coordinator's first turn and its workers (seen: the first command found no `node_modules`). Fix it on the person's yes with `t3_project_update` (`scripts`, the whole list, that flag changed).
- **Worktree cleanup.** T3 cleans worktrees once an hour by rules set globally or per project (Settings → the project → Worktree cleanup → Custom). Two of the rules remove the workspace of a live coordinator: **Delete unchanged worktrees** (no commits beyond the default branch: a ticket still in plan, or held on a plan question) and **Delete inactive worktrees** (a ticket held for days). **Delete settled worktrees** can remove a revived coordinator's workspace when the superseded session settles. Ask the person to set the project's cleanup to Custom with **Delete merged worktrees** on and inactive, settled and unchanged off, and **Keep worktrees with local changes** on `Uncommitted changes`. Check it in `~/.t3/userdata/settings.json`: `projectSettingsOverrides["<t3-project>"].worktreeCleanup` is `{"mode": "custom", "rules": {"worktreeOnMerge": true, "worktreeAfterDays": null, "worktreeSettledAfterDays": null, "worktreeUnchanged": false, …}}`. The dispatcher's sweep stays the last net.
- **Runtime mode `full-access`** on the thread that runs `run`, `once` or `resume`: a launched thread cannot have broader modes than the thread that launched it, and workers inherit their coordinator's. An approval request is never routed to a coordinator, so a supervised worker stalls on its first command. The scheduler's threads run `full-access` (verified).
- **Branches keep their names.** `t3_thread_launch` keeps the `branch` it is given (verified with Settings → Worktrees → branch naming `semantic`). A thread T3 names itself, such as the watcher's, gets a branch T3 makes up.

## Operations

| Operation | T3 Code |
|---|---|
| launch-coordinator | `t3_thread_launch` with `projectId` (`t3-project`), `title`, `workspaceStrategy {type: "worktree", baseRef, startFromOrigin: true, branch}`, `modelSelection {instanceId, model, options}` (**Candidates**), `runtimeMode: "full-access"`, `clientRequestId` `factory-<number>-<the claim token>` (a revive has a new token, so a new id), and the first message. It returns the `threadId` while the thread is `preparing`; `t3_thread_read` gives `worktreePath` once it is ready. Then make it quiet: `t3_thread_organize` `snooze` with `snoozedUntil` a year ahead. |
| launch-dispatcher | `t3_thread_launch` with `workspaceStrategy {type: "root"}`, the `scout` candidate, `runtimeMode: "full-access"`, `title` `factory dispatch <time>`, `clientRequestId` `factory-dispatch-<time>`. Not snoozed. |
| start-worker | `delegate_task` with the work order as `task`, `title` `<number> <step>`, `role` (`design` for `plan`, `implementation` for `build`, `test` for `verify`, `review` for `review`), `isolation: "shared"`, `target` the candidate **Routing** picked, mapped as **Candidates** says (`providerInstanceId`, `model`, `options`), `clientRequestId` `<number>-<step>-<round>-<time>` (unique per attempt: a replacement for the same step is a new task), `mode: "async"`. Record its `taskId` and `childThreadId` in the record's `tasks`. |
| send | `t3_thread_send` with `mode: "auto"`. To an idle coordinator it starts a turn, and it ends the thread's snooze (a pull request wake does not): the coordinator snoozes itself again at the end of the turn. To a worker: on a provider that steers (Claude, Cursor) it reaches the running turn; on one that cannot (Antigravity and other ACP agents) it is queued (`delivery: "queued"`) and read when the current turn ends. A finished worker is never sent new work: start a fresh one. |
| inspect | A coordinator or dispatcher: `t3_thread_read` on its thread: `status`, `activeRunId`, `pendingBackgroundTasks`, `recentRuns[0].status`, and with `view: "activity"` and a small `limit` its last output and its `error` items. **Live**: its latest run is not `failed`, `interrupted` or `cancelled`, or a newer one is queued; **dead**: otherwise, or the thread is archived or not found. A worker of your own: `task_status` (`status`, `workState`, `summary`, `hasPendingQuestion`). Another session's worker: `t3_thread_read` on its `childThreadId`. Providers able to take work: `orchestrator_capabilities` (a provider with `constraints` cannot). |
| link-pr | `link_pull_request` with `repository` and `number`. |
| watch-pr | `watch_pull_request` with `repository`, `number` and `until: "merged"`, then end the turn. Never watch the same pull request again on a wake: the watch stays on until the merge or the close. |
| unwatch-pr | `unwatch_pull_request`. |
| settle | `t3_thread_organize` `settle` (on your own thread it applies when the turn ends). |
| archive | `t3_thread_organize` `archive` on another session. For your own session, `settle` instead: archiving your own thread mid-turn ended the run with "The provider event stream closed unexpectedly" (seen 2026-11-27); so a dispatcher, as it archives itself, also archives the earlier settled ones (`t3_thread_list`, `titleContains: "factory dispatch"`, `settled: true`). |
| list-workspaces | `git worktree list --porcelain` in the main checkout; the records' `worktree` and `thread` say whose each one is. |
| close-workspace | In the workspace, the push check (INTERFACE.md); read its branch there with `git branch --show-current`. Then from the main checkout `git worktree remove <path>`, `git branch -D <branch>`, and `t3_thread_organize` `archive` on its thread. T3 has no tool that deletes a worktree. |
| revive | `t3_thread_launch` as launch-coordinator, with `workspaceStrategy {type: "existing_worktree", worktreePath}` when the workspace is still there; `{type: "worktree", baseRef: "origin/<branch>", startFromOrigin: true, branch: "<branch>"}` when it is gone and the branch is on the remote (`git ls-remote origin <branch>`), with `baseRef: "origin/<trunk>"` when it was never pushed; `{type: "root"}` when only **Close, merged** is left. The new thread cannot use the old thread's tasks (`task_status` and `task_cancel` answer `task_not_found`); it reads an old worker with `t3_thread_read` on the worker's `childThreadId` and stops it with `t3_thread_interrupt` on that `childThreadId` with `stop: true`. Stopping it starts a turn in the old coordinator thread, which then finds the claim names another session and settles. T3's metadata of a revived thread says `branch: null`: read the branch with git. |
| schedule-wakes | The watcher (below). `stop` deletes it with `delete_scheduled_task`. |
| flag-human | `t3_thread_organize` `unsnooze` and `pin` on the coordinator's thread, and `t3_thread_update` `rename` to `⏸ #<number> <slug>`, plus the brief on the tracker. Clear: `unpin`, rename back to `factory #<number> <slug>`, `snooze`. `mark_unread` fails while the thread's turn runs, which is always the case when it flags itself. |
| stop-worker | `task_cancel` with its `taskId`; another session's worker as in revive. |

## Events

Each event is a new turn of the coordinator's thread:

- A notification "Delegated task "<title>" finished", or a turn starting "Delegated task <taskId> (<title>) [completed]": `done`. Its result is the file its work order names; `task_status` gives its summary.
- "[failed]": `failed`. Read its `error` items for a usage limit (**Quota words**).
- "… has a question" or "… is blocked on a question": `question`. `t3_pending_request` `read` with the `threadId` and `requestId` it names, then `respond` with `answers` keyed by each question's `id`. When an option carries a `value`, answer with that `value`, not its label: an Antigravity worker answered `{"q1": "alpha"}` read "User Skipped", while `{"q1": "1"}` reached it as `alpha` (seen 2026-11-27). A Cursor worker has no question tool and asks with a message instead; answer it with send.
- A pull request watch: a turn starting "Update on pull request #<n> (<url>), which T3 Code is watching for you:" with one item per change: "Checks failed on <sha>: <check> <url>", "All <k> checks passed on <sha>", "The branch now conflicts with <trunk>"; or "Pull request #<n> … was merged into <trunk> by <who> as <sha>, so T3 Code stopped watching it", and the same for a close. Delays seen: one to two minutes.
- Not reported by the watch: comments and reviews written by the account T3 and `gh` run as (the project owner, as a rule), and label changes on the issue. The dispatcher covers both.
- No event at all for a worker whose `task_status` is `running` past `Wake timeout` with no new activity: `blocked`.

## Wakes: the watcher

1. Write `<memory>/wake-check.sh` (`set -eu`, so a failed `gh` call exits non-zero: the watcher then treats the board as changed). It reads only. It fingerprints the board: `gh issue list -R <owner>/<repo> --state open --limit 500 --json number,updatedAt,labels`, `gh pr list -R <owner>/<repo> --state open --limit 200 --json number,updatedAt,labels,headRefOid`, trunk's head (`gh api repos/<owner>/<repo>/commits/<trunk> --jq .sha`) and the state of each `Trunk checks` check on it (`gh api repos/<owner>/<repo>/commits/<sha>/check-runs --jq '[.check_runs[] | {name, status, conclusion}]'` and `/status`), hashed with `shasum -a 256`. `sh wake-check.sh` prints the hash; `sh wake-check.sh --changed` exits 0 when it differs from `<memory>/wake-fingerprint` (or that file is missing), 1 otherwise. The dispatcher writes `wake-fingerprint`.
2. When the memory index already names a `t3-watch`, update that schedule (`schedule_task` with its `scheduledTaskId`) instead of making a second one. Otherwise `schedule_task` with `title` `factory watch: <repo>`, `projectId` `t3-project`, `schedule` `{type: "interval", everyMs: <Wake timeout in ms>}`, `bindToCurrentThread: false`, `freshSession: true`, and this prompt (fill the paths):

   > Factory watcher for `<owner>/<repo>`. Run every command from `<main checkout>`, with the absolute paths given here. `res` is `node <factory>/scripts/resources.mjs --root <main checkout>`.
   > 1. When `res status` says `paused` and no record in `res ticket list` has a non-empty `tasks`, reply `paused` and stop.
   > 2. When `sh <memory>/wake-check.sh --changed` exits 1 and `res due --check` exits 1, reply `quiet` and stop.
   > 3. `res lock acquire --launcher watcher`. When it is refused, decide from the lock it prints:
   >    - `lock.thread` is empty and `expired` is false: a launch is under way. Reply `dispatcher running` and stop.
   >    - otherwise `t3_thread_read` the lock's thread with `view: "activity"`. Its latest run is `running`, `starting`, `preparing` or `queued`: reply `dispatcher running` and stop.
   >    - otherwise that dispatcher ended without releasing the lock. When its `error` items speak of usage, credits, a quota, a rate limit or "429", first `res quota block "<its candidate: t3_thread_configure on that thread, mapped back as Candidates says>" --until <the reset it names; else 24 hours for a weekly or monthly allowance or a plan without the model, else one hour from now> --ticket - --step dispatch --words "<the error's words>"`. Then, in every case, `res lock acquire --launcher watcher --reclaim` and go on to step 4.
   > 4. `res quota prune`, then pick the first candidate of the `scout` line of `<main checkout>/docs/agents/roles.md` whose line in `<memory>/providers.md` says `PASS` and that `<memory>/quota.md` does not block, mapped as `<factory>/references/t3.md` **Candidates** says. None: `res lock release`, reply `no scout candidate`, and stop.
   > 5. `t3_thread_launch` with `projectId` `<t3-project>`, `workspaceStrategy {type: "root"}`, that candidate, `runtimeMode: "full-access"`, `title` `factory dispatch <time>`, and the message: "Factory dispatcher for `<owner>/<repo>`, started by its watcher on the schedule the owner set up with `factory run` (the project's `AGENTS.md`, **Factory**, says what that means). Read `<factory>/SKILL.md`, then follow `<factory>/DISPATCHER.md` as the dispatcher. Main checkout: `<main checkout>`. Memory: `<memory>`. Lock token: `<the token res lock acquire printed>`. Your session id: `parentThreadId` in `orchestrator_capabilities`." Then at once `res lock thread <its threadId>`, and reply `launched <threadId>`.

3. Run it once (`run_scheduled_task_now`), find the watcher thread (`t3_thread_list`, `titleContains: "factory watch"`), and move it to the first candidate of the `scout` route with `t3_thread_configure` (`modelSelection`); later runs follow that thread's model. Record the task id and the thread id as `t3-watch` and `t3-watcher` in the memory index. The scheduler's thread runs `full-access`, and may sit in a worktree of its own when the environment's default for new threads is a worktree: the prompt's absolute paths keep it on the main checkout.

`once` and `resume` do steps 3 to 5 of the prompt themselves, from the session the person typed in, with `--launcher once` or `--launcher resume`.

A dispatcher reads its own session id as `parentThreadId` in `orchestrator_capabilities`.

## Candidates

T3 runs every candidate whose channel (`via`, else the provider) has a provider instance in `orchestrator_capabilities` without `constraints`. For `roles.mjs show`, pass those channels as `--channels`, named the way `roles.md` names them.

- **Where it goes:** `delegate_task` takes `target {providerInstanceId, model, options}`; `t3_thread_launch` and `t3_thread_configure` take `modelSelection {instanceId, model, options}`, with the same three values.
- **Provider instance:** `providerInstanceId` (or `instanceId`) is the instance of the channel: `anthropic` → `claudeAgent`, `openai` → `codex`, `cursor` → `cursor`, `antigravity` → `antigravity`; another channel maps to the instance of the same name. So `google/gemini-4-hydrogen via=antigravity` runs on `antigravity`, and `anthropic/claude-opus-5-5` on `claudeAgent`.
- **Model:** the model id as written, the way the instance lists it (its `search` input finds models beyond the short list).
- **Effort:** `effort=<level>` → the option that model lists whose values are effort levels. It differs by model, not only by instance (seen 2026-11-27): `effort` on `claudeAgent`; `thought_level` on `antigravity`; on `cursor`, `effort` for Claude models and `grok-4.6`, `reasoning_effort` for `grok-4.7` and Gemini models, none for `composer-2.5`; `variant` on `opencode`; `reasoning_effort` on `codex`. A level the model does not list is dropped, and the story or the journal says so.
- **Proposing routes** (`factory setup`): only models `orchestrator_capabilities` lists for a provider without `constraints`.

## Migration

Before `docs/agents/roles.md`, the roles lived in the coordinator provider's own files:

- `~/.claude/rules/smode-roles.md`, which Claude Code loads into every session of every project. Its plain lines `<role>: <alias> <effort>` become `anthropic/<model id the alias runs> effort=<effort>`.
- Its `route <role>: …` lines are T3 candidates with T3's ids. Convert each: the instance becomes `via`, unless it is the model's maker (`claudeAgent/claude-opus-5-5` → `anthropic/claude-opus-5-5`); the maker comes from the model id (`claude-*` → `anthropic`, `gemini-*` → `google`, `gpt-*` → `openai`, `grok-*` → `xai`, `composer-*` → `cursor`), so `antigravity/gemini-4-hydrogen thinking_level=high` (or `thought_level=high`) → `google/gemini-4-hydrogen effort=high via=antigravity`, and `cursor/composer-2.5` stays `cursor/composer-2.5`. Every effort option becomes `effort`.

After the project's file is committed, offer to delete the old file; until it is gone it keeps steering every Claude Code session.

A factory that ran the design with one coordinator for life kept `t3-coordinator` (its thread) and `live workers` in the memory index, and its watcher queued `mode once` into that thread. SETUP.md, **Converting older settings**, lists what changes.

## Work orders for other providers

- **Skills by absolute path.** A worker on another provider has none of these skills loaded (verified on Cursor and Antigravity). Every work order names the absolute path of smode's `SKILL.md`, the playbook to run, and the absolute path of every other skill it will need, resolved as smode's **Running a skill by name** says.
- **Shell when the file tool refuses.** Antigravity's file tools refuse paths outside the worker's workspace; the work order says to read and write such paths with the shell.
- **Results outside the repository** are written by path, with the same shell rule.
- **Not every provider can ask.** A Cursor worker has no question tool. Its work order says: when a question blocks the work, stop and report it in the result instead of guessing.
- **Commands run from the checkout.** Antigravity's shell has started outside the worker's checkout (seen: T3's attachments folder), and a Cursor worker has run its commands inside another checkout after reading a file there. Every work order says to run every command in the checkout and never inside a folder it names by absolute path. With `isolation: "shared"`, an Antigravity worker ran in the coordinator's worktree (verified: `pwd` and its file landed there).
- **Check where it wrote.** After a worker finishes and no other worker of the ticket still runs, check `git status` and that its writes stayed in the workspace. While a verifier and a reviewer share it, untracked files the verifier made are not a finding.

## Quota words

A session that stopped on a usage limit fails with the provider's message, in its `error` item (`t3_thread_read`, `view: "activity"`): words about usage, credits, a quota, a rate limit, a plan that does not include the model, "429", or a reset ("reset after 2h3m") mark it. Seen on Cursor: "Gemini 4 Carbon is not included in your weekly usage. Buy credits or switch to a Grok model to continue." and "Claude Opus 5.5 is not included in your weekly usage Buy credits or switch to a Grok model to continue."

## Smoke test helpers

- **Setup hooks finished:** `t3_project_read` lists the project's scripts; every one with `runOnWorktreeCreate: true` has `async: false`, so T3 holds the first turn until they end (verified in the spike). The smoke coordinator records, on its first command, whether what the script makes is there (its marker file, or `node_modules` for an install); with no such script, it records `no setup script`.
- **A scheduled run:** `list_scheduled_tasks` gives the schedule's `boundThreadId` and `lastRunStatus`; `t3_thread_read` on that thread shows the run's reply. Delete the schedule with `delete_scheduled_task` and archive the thread.
- **Your own session id:** `parentThreadId` in `orchestrator_capabilities`.

## Revive test (setup smoke test)

1. From the smoke coordinator, start worker `smoke sleeper` that waits five minutes in the foreground (`end=$(( $(date +%s) + 300 )); until [ $(date +%s) -ge $end ]; do sleep 5; done`), then reports.
2. Launch a second thread with `existing_worktree` on that workspace. From it: `task_status` on the sleeper's task answers `task_not_found`; `t3_thread_read` on its `childThreadId` shows it running; `t3_thread_interrupt` with `stop: true` stops it.
3. PASS when the second thread's `pwd` and `git branch --show-current` are the workspace's and the sleeper ends `interrupted`.

## Traps

- A launched thread starts from `baseRef` on the remote only with `startFromOrigin: true`; without it, from this checkout's commit.
- A finished child keeps its thread, but a new round is always a new `delegate_task`; a follow-up to a finished child does not reopen its task.
- Approvals are not routed; questions are. A Cursor worker has no question tool at all (**Work orders for other providers**).
- `interactionMode: "plan"` is not a read-only guard: never set it.
- A message ends a thread's snooze; a pull request wake does not. Every coordinator turn that ends unsnoozed sends a "finished" notification to the phone.
- T3 has no tool that deletes a worktree; close-workspace does it with git, on the path a record names, never on one matched by commit or by the `t3/` prefix: a person's worktree and a watcher's sit at the same trunk commit, and a cleanup by commit once removed both.
- A launch on an existing pull request's branch has no upstream: push with `git push origin HEAD:<branch>`.
- Claude Code's shell refuses a bare `sleep`, even in the foreground; a step that must wait loops on a condition (`until <check>; do sleep 5; done`), on every provider.
- A Claude worker moves a command longer than its shell timeout to the background and ends its turn; T3 then reports the task `completed` while the command still runs, and its result is missing. Work orders say to run commands in the foreground and wait, and a `done` without its result file is handled as **Failed workers** says.
