# T3 Code

Verified on T3 Code 0.1.9 (Beta, macOS) with Claude as the coordinator and Claude, Cursor and Antigravity workers. T3 runs a provider's own agent and adds one orchestration layer through its `t3-code` tools; the factory is the only skill that uses it to run workers. Use the `t3-code` tools of the coordinator's thread; they load late, so look each one up once before you call it absent.

## Before the first wake

- **The coordinator is one thread for life.** Tasks belong to the thread that started them (`task_status` and `task_cancel` refuse another thread's tasks), so never move the factory to a new thread while workers live. Record this thread's id (`parentThreadId` in `orchestrator_capabilities`) as `t3-coordinator` in the memory index.
- **It runs in the project root**, not in a worktree: every worker's worktree starts from the commit this checkout is at. The coordinator never edits code, so the checkout stays clean.
- **Runtime mode `full-access`** (or `auto`) on this thread: workers inherit it, and an approval request is never routed to the coordinator, so a supervised worker stalls on its first command.
- **Worktree cleanup** on in T3's settings (Settings → Worktrees → Cleanup: after the thread settles, after merging), as a second net behind close-workspace.
- **Worktree branch naming**: a static prefix (Settings → Worktrees), so T3 does not rename a worker's branch while it works.

## Operations

| Operation | T3 Code |
|---|---|
| open-workspace | In the main checkout: `git fetch origin`, then `git merge --ff-only origin/<trunk>` (stop and say so when it is not a fast-forward). The workspace itself is created by start-worker: every step is a fresh worktree. The ticket's branch on the remote carries the work between steps, and every work order names it: "start with `git fetch origin`; when `origin/<branch>` exists, `git reset --hard origin/<branch>`; push with `git push origin HEAD:<branch>`". |
| start-worker | `delegate_task` with the work order as `task`, `title` `<number> <step>`, `role` (`design` for `plan`, `implementation` for `build`, `test` for `verify`, `review` for `review`), `isolation: "worktree"`, `target` the candidate **Routing** picked, mapped as **Candidates** says (`providerInstanceId`, `model`, `options`), `clientRequestId` `<number>-<step>-<round>`, `mode: "async"`. Record the `taskId` and `childThreadId` in the memory index under `live workers`. |
| wait-events | Nothing to call. A finished worker starts a new turn in this thread ("Delegated task … [completed]" or "[failed]"); a question arrives as a notice; a watched pull request wakes it too. Each such turn is a wake. |
| send | `t3_thread_send` to the worker's `childThreadId`, `mode: "auto"`, only to a running worker. On a provider that steers (Claude, Cursor), it reaches the running turn; on one that cannot (Antigravity and other ACP agents) it is queued (`delivery: "queued"`) and the worker reads it only when its current turn ends, as a new turn. A finished worker is never sent new work: start a fresh one. |
| inspect | One worker: `task_status` (`status`, `workState`, `summary`, `hasPendingQuestion`), and `t3_thread_read` on its `childThreadId` with `view: "activity"` and a small `limit` for its last output and its `error` items. Every worker: `task_status` for each `taskId` under `live workers`. Providers able to take work: `orchestrator_capabilities` (a provider with `constraints` cannot). |
| flag-human | `t3_thread_organize` `pin` on this thread and `t3_thread_update` `rename` with a `⏸ <number>` prefix, plus the brief on the tracker. `mark_unread` fails while this thread's turn is running, which is always the case during a wake; the turn's end notifies the phone instead. Clear: `unpin`, rename back. |
| stop-worker | `task_cancel` with its `taskId`. |
| close-workspace | Find the worktree from the worker's own thread: `t3_thread_read` on its `childThreadId` gives `worktreePath` and `branch`. Never pick a worktree by commit or by the `t3/` prefix: a person's worktree and the watcher's sit at the same trunk commit, and a cleanup by commit removed both. Run the push check there, then `git worktree remove <worktreePath>`, `git branch -D <branch>` (the name the thread gives now: T3 may have renamed it), and `t3_thread_organize` `archive` on its `childThreadId`. |
| resume | The coordinator thread does not change. A new session in it (a fresh-session wake, a restart) reads `live workers` from the memory index and inspects each; a live worker keeps its step. |
| schedule-wakes | The watcher (below). Cancel it with `schedule_task` (`scheduledTaskId`, `enabled: false`) to pause, `delete_scheduled_task` to stop. |

## Events

- A turn that starts with "Delegated task <taskId> (<title>) [completed]": `done`. Its result is the file its work order names; the `summary` is its report.
- "[failed]": `failed`. Before **Failed workers**, read its `error` items for a usage limit (**Quota** in the playbook; **Quota words** below).
- "… is blocked on a question": `question`. `t3_pending_request` `read` with the `threadId` and `requestId` it names, then `respond` with `answers` keyed by the question's `id`.
- A watched pull request's wake: the board changed; go on with the wake.
- No event at all for a worker whose `task_status` is `running` past `Wake timeout` with no new activity: `blocked`.

## Wakes: the watcher

T3's scheduler has no pre-wake check: every run is a model turn. So the schedule runs a cheap **watcher** thread, and only the watcher decides whether the coordinator wakes.

1. Write `<memory>/wake-check.sh`. It fingerprints what a wake would act on (open issues and pull requests with `gh … --json number,updatedAt,labels,headRefOid`, trunk's head through `gh api repos/<owner>/<repo>/commits/<trunk> --jq .sha`, `ls -lA <memory>/results`: `-lA`, never `-la`, whose `..` line is the memory folder, whose time changes each time the fingerprint is written, so every run would wake), keeps the fingerprint in `<memory>/wake-fingerprint`, and exits 0 when it changed or the file is at least an hour old, 1 otherwise. Workers' outcomes need no fingerprint: they wake the coordinator themselves.
2. `schedule_task` with `title` `factory watch: <repo>`, `schedule` `{type: "interval", everyMs: <Wake timeout in ms>}`, `bindToCurrentThread: false`, `freshSession: true`, and this prompt (fill the paths and the id):

   > Factory watcher. Run `sh <memory>/wake-check.sh`. When it exits 1, reply `quiet` and stop. When it exits 0, list the queue of thread `<coordinator thread id>` with `t3_queue` `list`; when a message containing `factory once` or `mode once` waits there, reply `already queued` and stop. Otherwise send that thread, with `t3_thread_send` `mode: "queue"`, the message `<wake prompt>`, and reply `woke`.

3. Run it once (`run_scheduled_task_now`), find the watcher thread it made (`t3_thread_list`, `titleContains: "factory watch"`), and move that thread to the first candidate of the `scout` route in `docs/agents/roles.md`, mapped as **Candidates** says, with `t3_thread_configure` (`modelSelection`). Later runs follow that thread's model. Record the task id and the watcher thread id as `t3-wake` and `t3-watcher` in the memory index.

**Wake prompt.** `Read <absolute path of factory/SKILL.md> and run it in mode once.`, with the path found as smode's **Running a skill by name** says. It starts a wake on every provider, however the skills were installed; a skill command such as `$software:factory once` depends on how the plugin is named and is not used.

## Candidates

T3 runs every candidate whose channel (`via`, else the provider) has a provider instance in `orchestrator_capabilities` without `constraints`. For `roles.mjs show`, pass those channels as `--channels`, named the way `roles.md` names them.

- **Provider instance:** `providerInstanceId` is the instance of the channel: `anthropic` → `claudeAgent`, `openai` → `codex`, `cursor` → `cursor`, `antigravity` → `antigravity`; another channel maps to the instance of the same name. So `google/gemini-4-hydrogen via=antigravity` runs on `antigravity`, and `anthropic/claude-opus-5-5` on `claudeAgent`.
- **Model:** the model id as written, the way the instance lists it (its `search` input finds models beyond the short list).
- **Effort:** `effort=<level>` → the option the instance takes for it: `effort` on `claudeAgent`, `thought_level` on `antigravity`, `reasoning_effort` on `cursor` and `codex`. A level the instance does not list is dropped, and the journal says so.
- **Proposing routes** (`factory setup`): only models `orchestrator_capabilities` lists for a provider without `constraints`.

## Migration

Before `docs/agents/roles.md`, the roles lived in the coordinator provider's own files:

- `~/.claude/rules/smode-roles.md`, which Claude Code loads into every session of every project. Its plain lines `<role>: <alias> <effort>` become `anthropic/<model id the alias runs> effort=<effort>`.
- Its `route <role>: …` lines are T3 candidates with T3's ids. Convert each: the instance becomes `via`, unless it is the model's maker (`claudeAgent/claude-opus-5-5` → `anthropic/claude-opus-5-5`); the maker comes from the model id (`claude-*` → `anthropic`, `gemini-*` → `google`, `gpt-*` → `openai`, `grok-*` → `xai`, `composer-*` → `cursor`), so `antigravity/gemini-4-hydrogen thinking_level=high` (or `thought_level=high`) → `google/gemini-4-hydrogen effort=high via=antigravity`, and `cursor/composer-2.5` stays `cursor/composer-2.5`. Every effort option becomes `effort`.

After the project's file is committed, offer to delete the old file; until it is gone it keeps steering every Claude Code session.

## Work orders for other providers

- **Skills by absolute path.** A worker on another provider has none of these skills loaded (verified on Cursor and Antigravity). Every work order names the absolute path of smode's `SKILL.md`, the playbook to run, and the absolute path of every other skill it will need, resolved as smode's **Running a skill by name** says.
- **Shell when the file tool refuses.** Antigravity's file tools refuse paths outside the worker's workspace; the work order says to read and write such paths with the shell.
- **Results outside the repository** are written by path, with the same shell rule.
- **Not every provider can ask.** A Cursor worker has no question tool. Its work order says: when a question blocks the work, stop and report it in the result instead of guessing.
- **Commands run from the worktree.** Antigravity's shell starts outside the worker's worktree (seen: T3's attachments folder), and a Cursor worker has run its commands inside the coordinator's checkout after reading a file there. Every work order says: "your checkout is the git checkout T3 gave you; run every command there, not from the shell's start folder and never inside a folder this order names by absolute path: those paths are only to read".
- **Check where it wrote.** After a worker finishes, check `git status` and that its writes stayed in its worktree: Antigravity has written outside it.

## Quota words

A worker that stopped on a usage limit fails with the provider's message, in its `error` item (`t3_thread_read`, `view: "activity"`): words about usage, credits, a quota, a rate limit, a plan that does not include the model, "429", or a reset ("reset after 2h3m") mark it. Seen on Cursor: "Gemini 4 Carbon is not included in your weekly usage. Buy credits or switch to a Grok model to continue." and "Claude Opus 5.5 is not included in your weekly usage Buy credits or switch to a Grok model to continue."

## Resume test (setup smoke test)

1. Start worker `smoke sleeper` (`sleep 300` in the foreground, then report) on a provider whose shell runs a bare `sleep` (not Claude), and record its `taskId` under `live workers`.
2. `schedule_task` with `schedule` `{type: "once", runAt: <now + 2 minutes>}`, `bindToCurrentThread: true`, `freshSession: true`, and the prompt "Factory resume test: read the memory index, call `task_status` on every task under `live workers`, write the results to `<memory>/results/resume.json`, and reply with the file's path."
3. PASS when the file shows the sleeper as `running`: a fresh session in the coordinator's thread sees its live workers.

## Traps

- `isolation: "worktree"` starts from this checkout's commit, not from `origin`: a stale trunk here is a stale base for every worker.
- A finished child keeps its thread, but a new round is always a new `delegate_task`; T3's own guidance says so, and a follow-up to a finished child does not reopen its task.
- Approvals are not routed; questions are. A Cursor worker has no question tool at all (**Work orders for other providers**).
- `interactionMode: "plan"` is not a read-only guard: never set it.
- Antigravity's file tools refuse paths outside the worktree, its shell starts outside it (T3's attachments folder), and it has written outside it; work orders say to run every command from the checkout, and the provider check records `pwd`.
- Every coordinator turn that ends sends a "finished" notification to the phone; snooze the coordinator thread to keep them quiet.
- T3 has no tool that deletes a worktree; close-workspace does it with git, on the path the worker's thread names, never on one matched by commit.
- T3 may rename a worker's local branch while it works, a checker's too even though it works detached; read the branch from the worker's thread at close.
- Claude Code's shell refuses a bare `sleep`, even in the foreground; a step that must wait loops on a condition (`until <check>; do sleep 5; done`). The resume test's sleeper runs on another provider.
- A Claude worker moves a command longer than its shell timeout to the background and ends its turn; T3 then reports the task `completed` while the command still runs, and its result is missing. Work orders say to run commands in the foreground and wait, and a `done` without its result file is handled as **Failed workers** says.
