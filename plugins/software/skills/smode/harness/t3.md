# smode inside T3 Code

T3 Code runs a provider's own agent (Claude, Codex, Cursor, Antigravity, …) and adds one orchestration layer through its `t3-code` tools. Read this after the doc for the provider running this session (`claude-code.md` for Claude); this doc adds to it and wins where they differ. You are inside T3 when the `t3-code` tools (`delegate_task`, `orchestrator_capabilities`) are on offer. Those tools load late: look them up once before you call them absent.

## Actions

| smode action | T3 Code |
|---|---|
| See which providers and models can run | `orchestrator_capabilities` once per thread. A provider with `constraints` cannot take work. Models beyond the short list are found with its `search` input. |
| Spawn a worker | `delegate_task` with the work order as `task`, `target` from the role's route (`providerInstanceId`, `model`, and `options` such as `{effort: "high"}`), `isolation: "worktree"` for its own checkout, `role` (`implementation`, `research`, `review`, `test`, `design`, `general`) and `title`. Keep the `taskId`. |
| Wait for a worker | Do not poll. Its completion starts a new turn in this thread; end your turn when nothing else is left. |
| A worker asks a question | A notice arrives in this thread: read it with `t3_pending_request` (`list`, `read`), and answer with `respond` when the work order or the user's words settle it; otherwise ask the user. |
| Follow up with a worker | Every new round is a new `delegate_task` with consolidated scope, never `t3_thread_send` to a finished child. |
| Stop a worker | `task_cancel` with its `taskId`. |
| Read a worker's result | `task_status` (`summary`), or `t3_thread_read` on its `childThreadId` with `view: "activity"` for its tool calls and errors. |
| Ask the user | The provider's own question tool. A question from a worker is answered as above. |
| Schedule | `schedule_task`. |
| Watch a pull request | `watch_pull_request`, then end the turn; it wakes this thread on failed or passed checks, reviews and conflicts. Never from a child. |

## Routes

On T3 each role is a **route**: candidates in order, on different providers where possible. They live in the role file of the provider running the coordinator (for Claude, `~/.claude/rules/smode-roles.md`), one line per role under the plain role lines:

```
route thinker: claudeAgent/claude-opus-5-5 effort=high, cursor/claude-opus-5-5 effort=high, antigravity/claude-opus-5-5 thinking_level=high
```

Each candidate is `<providerInstanceId>/<model>` followed by its options. Take the first candidate that `orchestrator_capabilities` shows without constraints and that is not blocked for quota; a `reviewer` candidate must also be of another model family than the worker's. The Setup playbook writes routes from what `orchestrator_capabilities` offers.

## Work orders for other providers

- **Skills by absolute path.** A worker on another provider has none of this repository's skills loaded (verified on Cursor and Antigravity). Every work order names the absolute path of smode's `SKILL.md`, the playbook to run, and the absolute path of every other skill it will need, resolved by you as **Running a skill by name** says.
- **Shell when the file tool refuses.** Antigravity's file tools refuse paths outside the worker's workspace; the work order says to read and write such paths with the shell.
- **Results outside the repository** are written by path, with the same shell rule.
- **Not every provider can ask.** A Cursor worker has no question tool. Its work order says: when a question blocks the work, stop and report it in the result instead of guessing.
- **Read-only stays a rule.** Never set `interactionMode: "plan"` for it: Cursor then blocks every non-markdown write, result files included, and Antigravity does not block at all.
- **Permissions.** Approval requests are not routed to you. Workers inherit this thread's runtime mode; keep it `full-access` or `auto`, or the worker stalls on its first command.
- **Check where it wrote.** After a worker finishes, check `git status` and that its writes stayed in its worktree: Antigravity has written outside it.

## Worktrees and branches

- `isolation: "worktree"` starts the checkout from the commit this thread's checkout is at, not from the remote. Fetch and fast-forward first, or name the base in the work order.
- T3 names the worker's branch `t3/<id>` and may rename it. A worker that pushes uses `git push origin HEAD:<branch>`.
- T3 has no tool that deletes a worktree. Remove it with `git worktree remove` after checking nothing is unpushed, then archive the child thread with `t3_thread_organize`.

## Quota

A worker that stopped on a usage limit fails with the provider's message. Read it with `t3_thread_read` (`view: "activity"`, the `error` item): words such as "usage limit", "rate limit", "429" or "reset after 2h3m" mark it, and the reset time, when given, is in the text. Block that candidate until then, or for an hour when no time is given, and move to the next candidate of the route.
