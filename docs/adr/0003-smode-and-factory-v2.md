# One mode skill with playbooks, models chosen at delegation, and a factory v2 built on it

The skills ran on several harnesses (Claude Code, Codex, Oh My Pi) and now also on many providers through T3 Code (Claude, Cursor, Antigravity). Three things broke down. There was no common entry point: 26 skills each fired on their own description. Factory v1's workers handed each step to a role agent (`planner`, `implementer`, `verifier`, `review-*`) only to pick its model, and those agents exist per platform, so a provider that does not load them cannot run the step and every provider change leaves their models stale. And T3 drives every provider through one orchestration layer, but each provider loads skills its own way, so a worker on Cursor or Antigravity saw none of this repository's skills (spike S3).

We add **`smode`**, a user-invoked **mode skill** in `software`, following pstack's `poteto-mode` (cursor/plugins, MIT): a trigger table, an always-pause list, delegation rules, and one short **playbook** per kind of task, whose steps call the existing skills by name. **Models are chosen when work is delegated**, from a per-machine **role** configuration (one **route** per role on T3), never from an agent definition. `smode` **finds a skill by name through a generated skills index**, in this order: the harness's own invocation, the repository checkout, the harness's installed plugin (`installPath`), the harness's marketplace clone; relative paths work only inside one plugin (spike S1), and reading the file also runs user-invoked skills that a skill tool refuses. The knowledge in the role agents moves into the playbooks `plan-ticket`, `ticket`, `verify` and `review`. **Factory v2** is a new `factory-v2` skill beside **a frozen v1**: it keeps v1's ticket chain, merge guard, memory and ten-operation interface, runs each worker step as a `smode` playbook on the model its role routes to, skips routes out of quota, and qualifies each provider in its smoke test. **T3 is one reference**, like Orca: its tool names live only in `smode/harness/t3.md` and `factory-v2/references/t3.md`. **Read-only is a rule written in the work order**, never a mode: T3's plan mode blocks writes on Cursor, not on Antigravity, and on Cursor it also blocks the result file (spike S4).

## Consequences

- Factory v1, `software-claude`, `software-omp` and `references/orca.md` stay unchanged while v2 is proven. Removing the role agents is a later decision.
- Skills and playbooks still never name an agent's tools. Only the harness docs of a mode skill and the references of a factory do.
- On Oh My Pi, `smode` spawns workers from OMP's bundled agents with an exact `provider/model` taken from a user-level role, because OMP refuses role aliases per call and approves only models that user-level roles name (spike S6).
- On T3, a provider without an ask tool in a child (Cursor) reports `failed` with its question, and the coordinator holds the ticket; quota is read from the error text, because T3 passes agents only the message (spike S5).
- The validator enforces what must be exact: the skills index matches the repository, every skill a playbook names exists, and harness tool names stay out of the core.
- Spike results: `.scratch/smode-factory-v2/research/`.
